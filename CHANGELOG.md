## [0.0.76] - 2026-08-09
### ### Changed
- Trimmed every tool description and parameter schema. The `tools/list` payload an AI client receives on connect went from **41,718 to 28,527 characters (roughly 10,430 to 7,130 tokens, a 32% cut)** with no change to behaviour -- measured by querying the running server, not estimated. That payload is re-sent every conversation, so it is a recurring cost paid by every user of every client.
- Measuring first showed the assumption "19 tools is too many" was wrong: tool *count* was never the problem, description *length* was. Average cost was ~550 tokens per tool where 100-200 is typical, and the single largest (`excel_update_module_code`) accounted for 14% of the total on its own. Consolidating tools was considered and rejected -- the eight `excel_list_*` tools take genuinely different parameters and return different shapes, so folding them into one discriminated tool would make each variant harder for an agent to call correctly, not easier.
- What was cut: rationale for past design decisions, enumerations of things the response already contains (e.g. all nine `lintWarnings` rule categories), restatements of error text that arrives anyway, and cross-references to this project's own history. What was deliberately kept: how to call the tool, and anything surprising enough to cause a mistake -- the required dryRun/confirm flow, that UserForms cannot be created, that names must be verified before being referenced because a mismatch only fails at runtime, and that nothing is ever saved to disk.
- Also fixed real duplication: the `workbook`/`workbookPath` parameter descriptions were repeated verbatim across 14 and 17 tools respectively, and are now stated once, concisely, in each.
- Verified after the change: full build, all 48 unit tests, and a live call to every one of the 19 tools against the real test workbook -- read-only tools, the write path's dry-run, and an error path. All behave exactly as before.

## [0.0.75] - 2026-08-09
### ### Added
- `excel_update_module_code` can now overwrite **UserForm (.frm) modules**, which it previously refused outright with `ERR_UNSUPPORTED_MODULE_TYPE`. Only the form's code-behind is replaced, via the same `CodeModule.DeleteLines` + `AddFromString` path already used for Sheet/ThisWorkbook Document modules; the Designer side -- the controls, their positions/sizes, and the paired `.frx` binary -- is never touched. Motivated by working through a concrete requirement (enter an ID on a form, pull matching rows from an inventory sheet, edit them, write them back on a button click): the form's *layout* still has to be built by a human, but with this the *logic* can be written end-to-end by an agent, which was the actual blocker.
- Confirmed on real hardware before implementing, since the old refusal implied this was unsafe: writing through this path leaves all of the form's controls intact, and preserves the module-level `Attribute` lines -- including `VB_PredeclaredId = True`, which is what makes `UserForm1.Show` work without explicitly instantiating the form. UserForms also turn out to carry no per-procedure `Attribute` lines at all (macro shortcut keys are assigned to macros visible in Excel's macro list, and a form's `Private` event handlers never appear there), so the shortcut-key loss that Document modules warn about does not apply here -- `willLoseShortcutAttributes` correctly stays `false`.
- Creating a *new* UserForm is still not supported (`moduleType` accepts only `standard`/`class`): that would mean an agent generating form layout, which remains deliberately out of scope. The tool description now says so explicitly and points at `excel_list_form_controls` for confirming a control exists before writing code that references it.
- Implemented as a dedicated branch inside `import_single_module.ps1` (the MCP-only entry point) rather than by touching the shared `Import-ModuleToVBProject`, which the VS Code "Import Module To VBA" command also uses and which correctly routes `.frm` files to the `.frx`-aware `Import-FormToVBProject`. Same containment approach as the create-module mode in v0.0.64. Backups for forms are now written with a `.frm` extension instead of falling through to `.bas`.
- Verified live: wrote new code into a UserForm carrying 9 controls and confirmed all 9 survived unchanged, read the new code back, restored the original code through the same tool, and re-checked that a plain `.bas` module still writes as before.

### ### Fixed
- `excel_list_form_controls` now normalizes four more control types that v0.0.69 had to leave as raw COM interface names for lack of a real form to check them against: `IMdcText` → `TextBox`, `ITabStrip` → `TabStrip`, `IMultiPage` → `MultiPage`, `IScrollbar` → `ScrollBar`. These surfaced from a test form that had grown the extra controls -- the v0.0.69 design of returning unrecognized types raw rather than guessing is what made them identifiable at a glance. All nine controls on that form now report their familiar VBA names.

## [0.0.74] - 2026-08-09
### ### Fixed
- Converted `src/server/server.ts` from Shift-JIS (CP932) to UTF-8, fixing a long-standing latent defect: the TypeScript compiler reads source files as UTF-8, so a CP932-encoded source was being misread on every build, leaving **1949 replacement characters (U+FFFD) in the compiled `dist-server/server.js`**. It was harmless in practice -- every non-ASCII character in the file turned out to be inside a comment, with no Japanese in any functional string literal -- but it also meant the mojibake inside embedded PowerShell scripts' `#` comment lines was being passed to `powershell.exe` on every invocation. After conversion the compiled output contains zero replacement characters.
- Verified the change cannot affect the contract with the PowerShell scripts (arguments in, JSON out), since that was the main risk: compiled the converted source with `removeComments: true` and byte-compared it against the same build of the pre-conversion source. The only differences were **18 lines, all of them `#` comment text inside embedded PowerShell scripts** -- on every one of those lines the executable code before the `#` was byte-identical. Values passed to `-File` scripts come from runtime MCP parameters rather than source literals, and stdout is explicitly UTF-8 on both sides, so neither is affected by the source's own encoding.
- Also confirmed live against the real test workbook: `ping`, `excel_list_modules`, `excel_get_module_code` (success and `module_not_found`), and both literal and regex `vba_search_code`. The search tool matters most here because its embedded PowerShell contains most of the changed comment lines -- its results still correctly report `exportExt`/`compType`, which are produced by the exact `switch` block whose trailing comments changed.
- Beyond the compiler defect, this removes the need for the byte-level PowerShell patching previously required to edit this one file; it can now be edited with ordinary tooling like every other source file in `src/server/`. That editing technique had been a recurring source of trouble in its own right (see the backtick-escape incident recorded in v0.0.58).

## [0.0.73] - 2026-08-09
### ### Added
- Extracted `classifyResult`/`classifyResultWithRedaction` (v0.0.72's success/error/redaction branching logic, shared by most COM-backed tools) out of `server.ts` into a new pure-logic file, `src/server/responseClassification.ts`, and added 10 `node:test` assertions for it. Prompted directly by the user, after thorough manual verification of v0.0.72's redaction feature, asking a pointed question: shouldn't changing branching logic that affects an existing route also come with a regression test exercising that existing route? It didn't, for this specific logic -- like the rest of `server.ts`, it was previously only exercised by disposable, one-off JSON-RPC harness scripts against a real Excel instance, with no coverage that survives past the session that wrote it.
- Neither function actually touches COM or spawns PowerShell -- they only interpret text some other caller already obtained -- so nothing about this move required compromising the project's established boundary (pure logic gets persistent `node:test` coverage; anything that needs live Excel doesn't). It had simply never been split out, since it predates the pure-logic-file convention established later in this project's history.
- Caught during the extraction itself: the new file's exported return type, written as a named `interface`, made `tsc` reject every `server.tool(...)` call site with an index-signature mismatch against the MCP SDK's callback type -- even though the original inline (unnamed) object type had compiled fine in the exact same position. Switched to a `type` alias for the same shape, which resolved it; a concrete instance of TypeScript's assignability rules treating named interfaces and structurally-identical type aliases differently against a target type that itself has an index signature.
- Verified: full unit-test suite (48 assertions total) passes: existing tests unaffected, confirming the refactor didn't change any existing tool's browsing/success path; new tests specifically cover the success/`ok:false`/`ERR_`-prefixed/non-JSON/redaction branches that previously had no persistent coverage. Live smoke-tested afterward against the real test workbook (`ping`, `excel_list_modules`, `excel_get_module_code` success and `module_not_found` paths) to confirm the extraction didn't change end-to-end tool behavior.

## [0.0.72] - 2026-08-09
### ### Added
- All tools that return verbatim (or near-verbatim) VBA source text now mask hardcoded credentials before the response leaves this process: `excel_get_module_code`'s `code`, `excel_update_module_code`'s dry-run `currentCode`/`newCode`, `vba_search_code`'s per-hit `snippet`, and the `raw` field in every finding from `vba_list_dependencies`/`vba_list_references`/`vba_list_variable_scopes` (12 call sites across `dependencyScan.ts`/`referenceScan.ts`/`variableScopeScan.ts`). Motivated directly by a user's concern raised while reviewing an unrelated tool proposal: any tool returning real VBA source is a channel through which a hardcoded password or API key reaches a cloud-hosted AI model, and none of the existing tools did anything about that.
- New pure-logic module `src/server/secretRedaction.ts` (`redactSecrets` for a single line, `redactCodeText` for a full multi-line module) matches four patterns -- direct assignment to a credential-shaped identifier (`Password`/`Pwd`/`ApiKey`/`SecretKey`/`Secret`/`Token`/`AccessKey`/`ClientSecret`), a credential embedded inside a larger string such as an ADODB connection string, and HTTP `Authorization` headers (both via `.setRequestHeader` and a generic assignment) -- and replaces only the captured value with `[REDACTED]`, leaving the rest of the line intact so the fact that a hardcoded credential exists is still visible as a code-quality signal.
- **Always applied, with no opt-out.** An AI agent has no way to know in advance that it should ask for redaction before a secret is already in its context, so making this optional would defeat the point. This is best-effort regex matching, not a real parser -- a secret assigned to a variable with no recognizable keyword nearby will not be caught, and this is stated plainly in the affected tools' descriptions and in `docs/AI_USAGE.md`.
- `excel_get_module_code`/`vba_search_code` needed a new shared helper, `classifyResultWithRedaction`, since they previously passed the PowerShell subprocess's JSON output straight through unparsed; it now parses the payload, redacts the specified field(s) (a top-level string field, or one field within an array of hit objects), and falls back to the original unparsed passthrough if JSON parsing fails, to avoid changing any existing error-path behavior. `excel_update_module_code`'s dry-run preview objects are constructed directly as plain TS objects and only needed their two code fields wrapped at construction time.
- **Known gap, explicitly out of scope this round**: `vba_analyze_flow`/`vba_render_flowchart` embed near-verbatim source fragments (condition expressions, `Err.Raise` arguments) as flowchart node labels via `scripts/VBA-FlowJson.ps1`, a separate PowerShell script with its own text-extraction logic at several call sites -- this is not yet redacted. Documented as a known remaining exposure in `docs/AI_USAGE.md` rather than silently left unmentioned.
- Caught by this feature's own unit tests before release: the connection-string pattern's value group (`[^;"]+`) was permissive enough to re-match text the identifier-assignment pattern (which runs first) had *already* redacted -- `Password = "hunter2"` became `Password = "[REDACTED]"` after the first pattern, then the second pattern's `\s*=\s*` backtracked to hand the leading space (and, in a related failed fix attempt, even the opening quote) to its own value group, corrupting the already-correct redaction into `Password =[REDACTED]"[REDACTED]"`. Fixed by requiring the connection-string pattern's captured value to start with a non-whitespace, non-quote character, which stops it from matching inside already-redacted output at all.
- Verified live against the real test workbook: created a module containing both a `Public Const API_KEY = "..."` and an ADODB connection string with an embedded `Password=...`, and confirmed all five exposure points (create-mode dry-run `newCode`, `excel_get_module_code`, overwrite-mode dry-run `currentCode`/`newCode`, and `vba_search_code`'s `snippet`) correctly redacted both secrets while leaving the surrounding code readable; test module removed afterward.

## [0.0.71] - 2026-08-06
### ### Added
- Two new read-only tools, `excel_list_conditional_formats` and `excel_list_data_validations`, completing the migration-blind-spot work started with `excel_list_formulas` (v0.0.70) -- both raised together by the user as the same category of hidden, code-invisible business logic: a cell's color can depend on a conditional-formatting rule, and a cell's allowed input (including a dropdown's actual choices) can depend on a data-validation rule, neither of which appears in VBA code or in the cell's own formula.
- `excel_list_conditional_formats` reads each cell's `FormatConditions` collection (a cell can have more than one rule). `excel_list_data_validations` reads each cell's single `Validation` object -- for type `List`, `exampleFormula1` is literally the dropdown's source (a literal comma-separated string or a range reference), directly answering the "list information" the user asked for by name.
- Both use `Range.SpecialCells` for efficient discovery (`xlCellTypeAllFormatConditions`/`xlCellTypeAllValidation`, mirroring `excel_list_formulas`'s use of `xlCellTypeFormulas`) and group results the same way, to avoid one-entry-per-cell blowups on filled-down rules. New technical wrinkle discovered and solved this round: unlike `Range`, neither `FormatCondition` nor `Validation` exposes an R1C1-style position-independent formula property, so grouping by the raw `Formula1`/`Formula2` string alone would fragment relatively-referenced rules by row, same problem `FormulaR1C1` solved for plain cell formulas. Fixed by calling `Application.ConvertFormula(formula, xlA1, xlR1C1, xlRelRowRelColumn, RelativeTo:=<the cell>)` on each rule's formula using its own cell as the anchor -- confirmed live that two cells with the row-shifted formulas `A5>10`/`A6>10` both convert to the identical `RC[-2]>10`, so they correctly land in the same group.
- `type`/`operator` are normalized to readable names only for the enum values that could be reasoned about with confidence from documented Excel constants; anything unrecognized is returned as its raw number rather than guessed, following the exact lesson from v0.0.69's MSForms control-type fix (a wrong-but-confident-looking name is worse than an honest raw number). None of the enum values could be verified live this round, since the available test workbook has neither feature -- flagged for the user to report back any observed `type`/`operator` values so unmapped ones can be added with real confidence, same as the earlier control-type fix.
- Verified live against the real test workbook for the empty-result and sheet-not-found paths on both tools; the enum-name mapping and the `ConvertFormula`-based grouping's real-world behavior (beyond the synthetic two-cell check above) still need confirmation against a workbook that actually has conditional formatting / data validation.

## [0.0.70] - 2026-08-05
### ### Added
- New read-only tool `excel_list_formulas`, addressing a migration-investigation blind spot raised directly by a user: a macro's output is often further processed by cell formulas (VLOOKUP, conditional logic, etc.) into what a human actually consumes, and none of the existing tools could see this at all -- `excel_read_range` only returns computed values (`Range.Value2`), and `vba_list_references`'s named-range/sheet detection only scans VBA *code text* via regex, never the actual contents of a cell. Porting only the VBA side of a workbook while missing this downstream spreadsheet-formula layer is a classic incomplete migration.
- Cells are grouped by their `FormulaR1C1` representation -- Excel's own position-independent form of a formula, where relative references are expressed relative to the cell rather than as absolute row/column numbers -- so a formula filled down across thousands of rows (e.g. the same VLOOKUP repeated in B2:B10000) collapses into one group with a `cellCount`, rather than returning thousands of near-identical entries (the same class of problem `vba_search_code`'s `maxResults`/`truncated` already guards against for full-text search results). Each group's `exampleFormula` is plain A1-style for readability; `addresses` lists up to 20 matching cells per group (`addressesTruncated:true` beyond that), and the whole response caps at 500 groups (`truncated:true` beyond that).
- Does not require the VBA Trust Center setting (confirmed live, same as `excel_list_worksheets`/`excel_list_defined_names`): `Worksheet`/`Range`/`SpecialCells` are all plain Excel object model, not `VBProject`.
- A sheet or range with zero formulas returns an empty `formulaGroups` array rather than an error -- `Range.SpecialCells(xlCellTypeFormulas)` throws a COM exception when nothing matches (confirmed live), caught and normalized to the empty-result case.
- Verified live against the real test workbook: correctly returned an empty result for both the default (whole `UsedRange`) and an explicitly-bounded range on sheets with no formulas, and correctly rejected a nonexistent sheet name. The workbook's real-world grouping behavior (a filled-down formula pattern actually collapsing into one group) could not be verified in this session, since none of the sheets in the available test workbook contain any formulas at all -- flagged for the user to confirm against a workbook that does.

## [0.0.69] - 2026-08-05
### ### Fixed
- Reported live (user tested `excel_list_form_controls` against a real UserForm with real controls, right after v0.0.67 shipped with an untested `type` field): `[Microsoft.VisualBasic.Information]::TypeName()`, called on a late-bound MSForms control via PowerShell COM automation, does NOT return the familiar VBA-side type name (`Label`, `ComboBox`, `OptionButton`, `Image`) -- it returns the control's raw internal COM interface/coclass name instead (`ILabelControl`, `IMdcCombo`, `IMdcOptionButton`, `ImageClass`), which an AI agent has no reason to recognize as meaning those familiar control types. This was exactly the gap flagged as unverified when the tool shipped (its one test-workbook UserForm was empty at the time), confirmed the moment a real form with real controls was tested.
- Investigated a more principled fix (CLSID lookup via `IPersist` + Windows Registry ProgID resolution) but the required COM interop type isn't available as a plain .NET type accelerator without a custom interop shim, and the three different raw naming conventions observed across just 4 controls (`I*Control`, `IMdc*`, `*Class`) meant guessing the remaining ~11 standard MSForms control types' raw names would risk shipping confidently wrong data. Landed on a deliberately conservative fix instead: a lookup table normalizing only the 4 control types confirmed live (`Label`/`ComboBox`/`OptionButton`/`Image`) to their familiar VBA names; any other control type is left as its raw interface name rather than guessed. The tool description now explains this explicitly, so an agent seeing an unfamiliar-looking type string knows it's still probably correct in substance, just not normalized yet.
- Verified live against the real UserForm1 (now containing one of each of the four confirmed types) -- all four now report the expected familiar name.

## [0.0.68] - 2026-08-04
### ### Added
- New read-only tool `excel_list_defined_names`, extending the same "verify before generating code that references it by name" pattern as v0.0.67's `excel_list_worksheets`/`excel_list_form_controls` to named ranges. Lists the workbook's actual `Names` collection (both workbook-scoped and sheet-scoped) with `name`, `refersTo`, `scope`/`scopeSheet`, `visible`, and `isBroken` (true when `refersTo` contains `#REF!`, meaning the name points at something that was deleted). `vba_list_references`' named-range reporting only scans existing VBA code text via regex for likely references -- it has no visibility into the workbook's actual Names collection, so a reference to a name that doesn't exist (or no longer resolves to anything) was previously undetectable in advance. Does not require the VBA Trust Center setting (confirmed live, same as `excel_list_worksheets`): `Workbook.Names` is part of the plain Excel object model, not `VBProject`.
- The `isBroken` flag was validated against a genuine real-world case found while researching this feature: the project's own real test workbook has exactly one defined name (`ConvertButton`), and it turned out to already be broken (`refersTo` was `=CIDR!#REF!`, from something -- likely a button/shape -- that had been deleted at some point). This was found and confirmed correctly flagged before the feature was even fully implemented, which is about as strong a validation as this kind of advisory check gets.
- Scope detection (`workbook` vs `sheet`, plus `scopeSheet` when sheet-scoped) is done via `Name.Parent` (comparing whether the parent is the workbook itself or a specific worksheet) rather than string-parsing the `name` field for a `SheetName!` prefix, since that prefix convention was not independently verified against a sheet-scoped name in this session's test workbook (it has none) and `.Parent` is the more direct, unambiguous signal.

### ### Documentation
- Recorded an explicit, permanent design decision (in `excel_update_module_code`'s own tool description and in `docs/AI_USAGE.md`'s write-safety section): **the workbook is never saved to disk automatically**, and there is no separate "save" tool. This was raised as a possible gap, then deliberately rejected: since `lintWarnings` is a regex-based heuristic rather than a real VBA parser, the tool cannot guarantee written code is free of syntax errors -- automating the save step would risk silently persisting broken code to the `.xlsm` file before a human ever looks at it. The current behavior (write lands in the live Excel process; a human decides whether/when to save after checking it in Excel) is being kept as an intentional human checkpoint, not treated as a missing feature.

## [0.0.67] - 2026-08-04
### ### Added
- Two new read-only tools, `excel_list_worksheets` and `excel_list_form_controls`, added after discussing a realistic AI-driven macro-authoring workflow: generated VBA code typically references a worksheet by name (`Worksheets("...")`) or a form control by name (`UserForm1.TextBox1`) on faith, and a mismatch only surfaces as a runtime error, not at write time -- there was previously no way for an agent to check either in advance.
- `excel_list_worksheets` returns each worksheet's display name, VBA CodeName, index, and visibility (`visible`/`hidden`/`veryHidden`). A worksheet has two distinct names -- the display name (renamable, what string-based `Worksheets("...")` lookups use) and the CodeName (fixed at creation, what direct `Sheet1.Range(...)` references use, and the same string `excel_list_modules` reports as the module name for `componentType 100` entries) -- this is the first tool to expose that mapping. Does not require the VBA Trust Center setting (confirmed live before implementing): `Workbook.Worksheets` is part of the plain Excel object model, not `VBProject`, matching `excel_read_range`'s existing advantage over the VBA-code tools.
- `excel_list_form_controls` returns each UserForm's controls (name and type only, e.g. `TextBox`/`CommandButton`) by reading `VBComponents(name).Designer.Controls` (requires VBA Trust Center access, same as `excel_list_modules`). Optional `formName` narrows to one form; omitted, it returns every UserForm in the project in one call (same pattern as `excel_list_macros`'s optional `moduleName`). Control type is read via `[Microsoft.VisualBasic.Information]::TypeName()` (the same mechanism VBA's own `TypeName()` uses internally) -- confirmed live that `.Designer.Controls` access itself works without error, though the `type` value could not be verified against a real control in this session's test workbook (its one UserForm is empty); reviewed as correct by inspection.
- **Deliberately scoped to read-only existence checks.** Neither tool can create or rename a worksheet or form control -- whether an AI agent should be trusted to make structural changes like that (as opposed to writing VBA code, which is comparatively easy to preview/diff/undo) was an open question this round, so it was decided not to build that capability yet. Both tools' descriptions explicitly instruct an agent that finds a missing sheet/form to report it to the user for manual creation, rather than attempting any workaround.
- Verified live against the real test workbook: `excel_list_worksheets` correctly distinguished all three sheets' display/code names and hidden state; `excel_list_form_controls` correctly returned the one real UserForm (with its correctly-empty control list) both with and without `formName`, and correctly rejected a nonexistent form name (`form_not_found`) and a non-UserForm module name (`ERR_NOT_A_USERFORM`).

## [0.0.66] - 2026-08-02
### ### Added
- `duplicateProcedureWarnings` (v0.0.65) gained a second, lower-severity risk category. Found live within a day of shipping v0.0.65: a newly-added module's own Private helper procedure happened to share a name with two other modules' Public functions. Since v0.0.65's check only looked at Public procedures in `newCode`, this Private-vs-Public case was invisible to it entirely -- the collision was only found because an AI agent fell back to a manual full-text search across the whole project after being asked directly. Each `duplicateProcedureWarnings` entry now carries a `risk` field: `public_duplicate` (the v0.0.65 case -- newCode's own procedure is also Public, usually meaning a procedure was moved to a new module but the original copy was left behind) or `private_name_reused` (newCode's procedure is Private -- never a real runtime/compile collision, since VBA always resolves the same-module Private first, but still confusing to read since the name already means something Public elsewhere in the project).
- The OTHER module's side of the comparison is unchanged -- still only matches against that module's Public-equivalent procedures (a same-named Private procedure there was never checkable against anything outside its own module, and flagging Private-vs-Private matches everywhere would just be noise for an extremely common, entirely safe pattern).
- Verified with 2 new unit test assertions (bringing `duplicateProcedureScan.test.js` to 8) covering the new `private_name_reused` case and confirming Private-vs-Private (both sides) is still correctly unflagged, then re-verified live against the real test workbook: reproduced the exact reported shape (a new module's Private function colliding with an existing module's real Public function) and confirmed `risk:"private_name_reused"`, alongside a regression check that the original Public-vs-Public case still reports `risk:"public_duplicate"`. Both checks used `dryRun:true` only, so nothing was written to the real workbook.

## [0.0.65] - 2026-08-02
### ### Added
- `excel_update_module_code`'s dry-run response gained `duplicateProcedureWarnings`: an advisory, dry-run-only check for Public Sub/Function/Property names in `newCode` that already exist in some OTHER module of the project (Private procedures are excluded, since same-named Private procedures in different modules never actually collide in VBA). Motivation: reported live -- moving a Function to a new class module via the v0.0.64 create-mode left the original copy behind in the source standard module, unnoticed, because the tool only ever writes to the module it's told to; there was no separate signal that the "old" copy needed cleaning up too. Matches by bare identifier name regardless of Sub/Function/Property kind (a Function colliding with a same-named Sub elsewhere is exactly the kind of naming collision this exists to catch, per how the case was actually reported).
- Applies to both create mode and overwrite mode (the risk is the same either way), and never blocks the write -- same advisory tier as the existing `lintWarnings`.
- Implemented as a new pure-logic file, `src/server/duplicateProcedureScan.ts` (`listProcedureSignatures`, `findCrossModuleDuplicates`), following the established pattern of keeping COM-free regex-based scanning out of the Shift-JIS-encoded `server.ts`. Procedure-header matching mirrors `variableScopeScan.ts`'s Unicode-aware `RX_PROC_HEAD` (`\p{L}\p{N}_`, handles non-ASCII identifiers correctly per the v0.0.62 fix there) but additionally captures the visibility modifier, which that regex leaves non-capturing.
- Costs one extra COM round-trip per `dryRun` call (reads every module in the project via the existing `readAllModulesCode` helper, already used by `vba_list_dependencies`/`vba_list_references`/`vba_list_variable_scopes`), on top of the dry-run's own existing read -- accepted as a reasonable tradeoff for the safety this catches, and scoped to dry-run only (the `confirmToken`/write path is unaffected). If this extra read fails for any reason, the dry-run's core preview and `confirmToken` are unaffected -- `duplicateProcedureWarnings` just comes back empty rather than failing the whole call.
- Unit-tested with 6 assertions (`src/server/__tests__/duplicateProcedureScan.test.js`): visibility/kind/comment-line extraction, cross-kind name collision (Function vs. Sub), Private-procedure exclusion, target-module self-exclusion, case-insensitive matching (VBA identifiers are case-insensitive), and the empty-result case. Verified live against the real test workbook: a new module containing a Function name that collides with a real Public Function in an existing module was correctly flagged (including the exact colliding module and line), a non-colliding name correctly returned an empty array, and the same collision was also correctly caught in overwrite mode against a different existing module with the colliding name written as a Sub instead of the original's Function (confirming the kind-agnostic match). All three checks used `dryRun:true` only, so nothing was actually written to the real workbook.

## [0.0.62] - 2026-08-02
### ### Fixed
- **Reported live** (via Copilot Chat testing `vba_list_variable_scopes` against a real workbook, immediately after v0.0.61's release): a variable declared inside a procedure whose *name* contains non-ASCII characters (e.g. a Japanese procedure name, common in Japanese-language VBA codebases) was misclassified as module-scoped instead of procedure-scoped -- e.g. a `Dim` inside `Sub 出力処理()` came back as `scope:"module", declaredIn:null` instead of `scope:"procedure", declaredIn:"出力処理"`. Root cause: `variableScopeScan.ts`'s procedure-boundary regex (`src/server/variableScopeScan.ts`, added in v0.0.60) matched procedure names with plain `\w` (ASCII letters/digits/underscore only), unlike `VBA-FlowJson.ps1`'s equivalent `ParseProcedures` regex, which already used `[\p{L}_][\p{L}\p{N}_]*` (Unicode letter/number) to handle exactly this case correctly. A name that doesn't match `\w` doesn't just get mis-captured -- the entire line fails to match at all, so the procedure's boundary is never recorded, and everything inside it silently falls outside every procedure's line range for the rest of that scan.
- Same root cause affected the variable-name capture inside declaration lines (a Japanese-named variable's own declaration would similarly fail to parse) and the usage-search word-boundary check added in v0.0.61 (JS's `\b` is itself ASCII-`\w`-based, so even after fixing the name-capture regexes, a lookup for a Japanese-named variable would fail to find its own usages) -- both fixed the same way: Unicode-aware character classes (`\p{L}\p{N}_`, requiring the regex `u` flag) instead of `\w`, and a manual lookaround-based boundary (`(?<![\p{L}\p{N}_])...(?![\p{L}\p{N}_])`) in place of `\b` for the usage search specifically.
- Verified with a regression suite covering the original all-ASCII test scenarios (unaffected, confirming the fix doesn't change existing behavior) plus the exact failure pattern reported (a `Dim` inside a Japanese-named procedure, including finding its usage sites afterward), then re-verified against the real workbook and the exact procedure originally reported -- now correctly resolves to `scope:"procedure"` with the right `declaredIn`, and its usage sites are found correctly across the procedure.

## [0.0.52] - 2026-07-26
### ### Fixed
- Reported live: asking an agent for "the module list, macro list, and the specified sheet cell values" in one request caused **3 separate Excel.exe processes** to launch. Root cause: each MCP tool call spawns its own independent `powershell.exe` process, and if a client fires multiple tool calls concurrently (as Copilot Chat appears to for a multi-part request like this), each one's `Get-OrStartExcelApplication` independently checks `GetActiveObject` before any of the others' newly-launched Excel instance has registered -- so each one concludes "Excel isn't running" and launches its own redundant instance, racing the others.
- Fixed by serializing all Excel-COM-touching PowerShell invocations through an in-process queue in `server.ts` (wraps `execFileAsync` itself, so every existing call site across all 7 tools is covered without touching each one individually) -- only one PowerShell/COM operation is ever actually in flight at a time, regardless of how many MCP tool calls arrive concurrently. Verified live: repeated the exact 3-call scenario (module list + macro list + cell range, all against a workbook with Excel not yet running) and got exactly 1 Excel process, with only the first call reporting `launchedExcelPid` and the other two reusing it.

## [0.0.51] - 2026-07-26
### ### Fixed
- Reported live (a `vba_search_code` call with `query: 'Range("A5")'`): a `query` containing a double quote failed with a PowerShell parse error. Root cause: the query was embedded as `$reRaw=${JSON.stringify(params.query)}`, producing a backslash-escaped double-quoted string (JSON/JS convention) -- but PowerShell double-quoted strings don't treat backslash as an escape character, so `\"` closes the string early instead of representing a literal quote. Fixed by embedding the query as a single-quoted PowerShell string with `psq()`'s existing single-quote-doubling escape (the same convention already used for `moduleFilter`/`workbookFilter` on the same tool), which needs no escaping at all for embedded double quotes. Verified live: the original failing query now returns `ok:true`, and a second query containing a literal double-quoted string correctly matched an existing line in the workbook.

## [0.0.40] - 2026-07-26
### ### Added
- `excel_update_module_code` now uses optimistic concurrency control: the `confirmToken` returned by a `dryRun:true` call is bound to the module's code as it was at that moment, and the tool re-reads the module immediately before writing to recompute and compare the token. ### Notes
- **Limitation**: This tool **replaces existing** modules/classes/forms only; **adding new items is not supported**.  
  To create a new item, add & save a blank module/class/form in VBE, then export it.
- **Caution**: Do **not edit attribute lines** in exported `.frm` files  
  (`VERSION`, `Begin … End`, `Object = …`, `Attribute VB_*`).
